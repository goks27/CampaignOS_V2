## 3. Database (migrations)

All tables have `id uuid pk default gen_random_uuid()`, `created_at`, `updated_at`, `created_by`, `version int`, with a shared trigger maintaining `updated_at` and `version`. Foreign keys are indexed, along with campaign IDs, statuses, owners and dates.

| # | Migration | Contents |
|---|---|---|
| 1 | `enums` | `workspace_role` (admin, manager, team_member, viewer, worker); `campaign_stage` (the 7 PRD stages); `campaign_status`; `track_status`; `health`; `priority`; `task_status`; `campaign_role`; `activity_action` |
| 2 | `core` | `workspaces`; `profiles` (1:1 with `auth.users`, name, avatar, active); `workspace_members` (workspace, user, role, deactivated_at) |
| 3 | `clients_campaigns` | `clients`; `campaigns` (every PRD §5 field: stage, priority, status, health, design/dev/QA/UAT status, dates, staging/production URL, notes, `is_demo`); `campaign_members` (user, campaign_role); `journeys` (campaign, name, description, sort order, its own stage and track statuses) |
| 4 | `tasks` | `tasks` (campaign, journey nullable, title, description, assignee, status, priority, due date, plus `source_finding_id` and `source_requirement_id` left nullable for Phase 3); `task_comments` |
| 5 | `activity_notifications` | `activity_logs` (workspace, campaign, entity type and id, action, actor, `before`/`after` jsonb; append-only); `notifications` (user, type, entity, read_at) |
| 6 | `helpers` | SECURITY DEFINER, STABLE, fixed `search_path`: `auth_role()`, `is_admin()`, `is_manager_or_admin()`, `is_campaign_member(campaign_id)`, `can_read_campaign(campaign_id)`, `can_write_campaign(campaign_id)` |
| 7 | `rls` | RLS enabled on every table, with the policies in §4 |
| 8 | `triggers` | Activity logging on insert/update/delete of campaigns, journeys, campaign_members, tasks and task_comments. A notification goes to the assignee when a task is assigned or reassigned. `handle_new_user` creates the profile. |
| 9 | `rpc` | `import_campaigns(payload jsonb, dry_run bool)`: one transaction that returns planned creates, updates and errors, and rolls back when `dry_run`; `dashboard_summary()` |

Phase 1 creates no storage buckets (the first upload is the SOW, in Phase 2). The Notion CSV is parsed in the browser and never stored.

## 4. Permissions (RLS)

| | Admin | Manager | Team member | Viewer | worker |
|---|---|---|---|---|---|
| Campaigns, journeys | all, read/write | all, read/write | assigned only, read | assigned only, read | **none** |
| Campaign members | read/write | read/write | read (own campaigns) | read (own campaigns) | none |
| Tasks | read/write | read/write | read on assigned campaigns; update status of own tasks | read | none |
| Task comments | read/write | read/write | read/insert on assigned campaigns | read | none |
| Activity logs | read | read | read (assigned campaigns) | read (assigned campaigns) | none |
| Workspace members, roles | read/write | read | read | read | none |
| Notifications | own | own | own | own | none |

- "Assigned" means a row in `campaign_members`.
- `activity_logs` has no update or delete policy for anyone. Rows are written only by triggers.
- Invite-only: public sign-up is disabled in `config.toml` and the Auth settings. People are invited from the Supabase dashboard. A new user joins as a Viewer until an Admin changes their role. No Edge Functions and no service-role key anywhere in the repo.
- The `worker` role exists now and has no grants. It gets narrow SECURITY DEFINER functions in Phase 2.

**pgTAP tests (`supabase/tests/`):**
1. A team member cannot read a campaign they are not assigned to, including its journeys, tasks and activity.
2. A viewer cannot insert, update or delete anything.
3. The worker cannot read campaigns, journeys, tasks, profiles or members.
4. A team member can change the status of their own task but not reassign it or edit other fields.
5. Nobody can update or delete `activity_logs`. Every change to a campaign or task writes one log row.
6. A non-admin cannot change roles or deactivate members.
7. `import_campaigns` with `dry_run` leaves no rows behind.

## 6. Decisions (confirmed by Gokul, 3 Nov 2026)

1. **Task statuses:** To do, In progress, Ready for review, Done, Blocked.
2. **Campaign status** (separate from stage): Active, On hold, Completed, Archived.
3. **Track statuses** for design, development, QA and UAT: Not started, In progress, In review, Awaiting client, Changes requested, Approved. Set manually in Phase 1, labelled "Set by manager".
4. **Health:** On track, At risk, Blocked. Set manually by the manager.
5. **Manager access:** managers read and edit all campaigns.
6. **Workspace tabs:** as BUILD-PLAN says. Overview and Journeys are live; the others, including Tasks and Activity, show "Available in Phase N".
7. **Invites:** by hand from the Supabase dashboard. No Edge Function. The first Admin is promoted with a documented SQL statement. In the app, Admins change roles and deactivate members on the Team page.
8. **Demo data:** one clearly fake placeholder campaign ("Sample campaign", one journey, labelled "Demo / unverified") replaces the Gold Drop seed, local development only. CLAUDE.md's Demo data section is updated to match.

## 7. Risks

- **Supabase free tier pauses after about a week of inactivity.** Documented, with steps to resume.
- **The demo seed creates auth users.** It's dev-only by design, and the setup guide warns never to run it against production.
- **Manual track statuses could be mistaken for AI results.** They're labelled as set by a manager.
- **Lots of UI.** Phase 1 is the biggest phase by UI volume, so I'll report after each milestone rather than at the end.
